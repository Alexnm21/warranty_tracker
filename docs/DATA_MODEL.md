# Warranty Tracker — Data Model

## 1. Purpose

This document defines the data model used by the application: fields, types,
nullability, persistence representation, and the rules that govern them.

It is the source of truth for:

* Database schema definitions.
* Domain entity fields.
* Repository and DAO data mapping.
* Persistence-related validation.

Field-level requirements (required/optional, validation) are defined in:

`docs/FIELD_REQUIREMENTS.md`

Date-related business rules are defined in:

`docs/DATA_RULES.md`

The inclusive end-date rule is defined in:

`docs/WARRANTY_END_DATE_RULE.md`

---

# 2. Product

`Product` is the central entity. Phase 1 uses a single `products` table; no
additional tables are required.

## 2.1 Fields

| Field               | Dart type     | SQLite type | Required | User entered | Notes                                   |
| ------------------- | ------------- | ----------- | -------: | -----------: | --------------------------------------- |
| `id`                | `int?`        | `INTEGER`   |      Yes |           No | Primary key, auto-increment             |
| `name`              | `String`      | `TEXT`      |      Yes |          Yes | Trimmed, must not be empty              |
| `brand`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `model`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `store`             | `String?`     | `TEXT`      |       No |          Yes | Free text, empty value stored as `null` |
| `purchaseDate`      | `DateTime?`   | `DATETIME`  |      Yes |          Yes | Calendar date (time is irrelevant)      |
| `price`             | `int?`        | `INTEGER`   |       No |          Yes | **Integer minor currency units**        |
| `currency`          | `String?`     | `TEXT`      | Cont.    |          Yes | ISO 4217; required when `price` set     |
| `serialNumber`      | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `warrantyStartDate` | `DateTime?`   | `DATETIME`  |      Yes |          Yes | Calendar date, inclusive                |
| `warrantyEndDate`   | `DateTime?`   | `DATETIME`  |      Yes |          Yes | Calendar date, inclusive                |
| `notes`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `createdAt`         | `DateTime?`   | `DATETIME`  |      Yes |           No | Generated by the application            |
| `updatedAt`         | `DateTime?`   | `DATETIME`  |      Yes |           No | Managed by the application              |

Notes:

* The domain entity keeps `id`, `purchaseDate`, `warrantyStartDate`,
  `warrantyEndDate`, `createdAt`, and `updatedAt` nullable so records can be
  composed before validation and persistence. Persistence enforces the
  required fields defined in `FIELD_REQUIREMENTS.md` §2.
* Optional string fields are trimmed before persistence; empty strings are
  never stored — they become `null`.
* Date fields represent calendar days (`DateTime(y, m, d)` in local time).
  Time of day, time zones, and UTC conversion must not affect date semantics
  (`DATA_RULES.md` §11).

## 2.2 Price

`price` is stored as an **integer in minor currency units**. Floating-point
values must never be persisted for monetary amounts (`FIELD_REQUIREMENTS.md`
§10).

```text
899.99 EUR  →  89999
0.00 EUR    →  0
```

Rules:

* `price` must not be negative. Zero is valid.
* `price == null` → no price provided; `currency` may be omitted.
* `price != null` → `currency` must be known (ISO 4217 code).
* The application default currency is `EUR`, applied explicitly when the
  user provides a price without choosing a currency.

Conversion to a decimal value happens only at presentation time.

## 2.3 Warranty Status (derived)

`warrantyStatus` is **derived**, never persisted (`DATA_RULES.md` §17):

```text
today < warrantyStartDate              → future
warrantyStartDate <= today <= end      → active
today > warrantyEndDate                → expired
```

* `warrantyEndDate` is inclusive: the warranty expires the day **after**
  `warrantyEndDate` (`WARRANTY_END_DATE_RULE.md`).
* The status is calculated in the domain layer from
  `warrantyStartDate`, `warrantyEndDate`, and the current calendar date. The
  UI must never calculate it independently.
* `purchaseDate` does not participate in the calculation.

## 2.4 Validation

Minimum validation before persistence:

```text
name              != null and not blank
purchaseDate      != null
warrantyStartDate != null
warrantyEndDate   != null
warrantyStartDate <= warrantyEndDate
price             == null or price >= 0
currency          known when price != null
```

The only required ordering rule between dates is
`warrantyStartDate <= warrantyEndDate`. There is intentionally no required
relationship between `purchaseDate` and the warranty range
(`DATA_RULES.md` §6).

## 2.5 Persistence Rules

* `create`: the application sets `createdAt` and `updatedAt`.
* `update`: `id` and `createdAt` are preserved; `updatedAt` is refreshed.
  Changing dates never implicitly changes other dates (`DATA_RULES.md` §14).
* Search is case-insensitive over `name`, `brand`, `model`, `store`, and
  `serialNumber`, executed by the database.
