# Warranty Tracker — Data Model

## 1. Purpose

This document defines the data model used by the application: fields, types,
nullability, persistence representation, and the rules that govern them.

It is the source of truth for:

* Database schema definitions.
* Domain entity fields.
* Repository and DAO data mapping.
* Persistence-related validation.

Field-level requirements (required/optional, validation) are defined in:

`docs/FIELD_REQUIREMENTS.md`

Date-related business rules are defined in:

`docs/DATA_RULES.md`

The inclusive end-date rule is defined in:

`docs/WARRANTY_END_DATE_RULE.md`

---

# 2. Product

`Product` is the central entity. Phase 1 introduced the single `products`
table; Phase 2 adds the `product_documents` table described in section 3.

## 2.1 Fields

| Field               | Dart type     | SQLite type | Required | User entered | Notes                                   |
| ------------------- | ------------- | ----------- | -------: | -----------: | --------------------------------------- |
| `id`                | `int?`        | `INTEGER`   |      Yes |           No | Primary key, auto-increment             |
| `name`              | `String`      | `TEXT`      |      Yes |          Yes | Trimmed, must not be empty              |
| `brand`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `model`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `store`             | `String?`     | `TEXT`      |       No |          Yes | Free text, empty value stored as `null` |
| `purchaseDate`      | `DateTime?`   | `DATETIME`  |      Yes |          Yes | Calendar date (time is irrelevant)      |
| `price`             | `int?`        | `INTEGER`   |       No |          Yes | **Integer minor currency units**        |
| `currency`          | `String?`     | `TEXT`      | Cont.    |          Yes | ISO 4217; required when `price` set     |
| `serialNumber`      | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `warrantyEndDate`   | `DateTime?`   | `DATETIME`  |      Yes |          Yes | Calendar date, inclusive                |
| `notes`             | `String?`     | `TEXT`      |       No |          Yes | Empty value stored as `null`            |
| `createdAt`         | `DateTime?`   | `DATETIME`  |      Yes |           No | Generated by the application            |
| `updatedAt`         | `DateTime?`   | `DATETIME`  |      Yes |           No | Managed by the application              |

Notes:

* The domain entity keeps `id`, `purchaseDate`, `warrantyEndDate`, `createdAt`,
  and `updatedAt` nullable so records can be composed before validation and
  persistence. Persistence enforces the required fields defined in
  `FIELD_REQUIREMENTS.md` §2.
* Optional string fields are trimmed before persistence; empty strings are
  never stored — they become `null`.
* Date fields represent calendar days (`DateTime(y, m, d)` in local time).
  Time of day, time zones, and UTC conversion must not affect date semantics
  (`DATA_RULES.md` §11).

## 2.2 Price

`price` is stored as an **integer in minor currency units**. Floating-point
values must never be persisted for monetary amounts (`FIELD_REQUIREMENTS.md`
§10).

```text
899.99 EUR  →  89999
0.00 EUR    →  0
```

Rules:

* `price` must not be negative. Zero is valid.
* `price == null` → no price provided; `currency` may be omitted.
* `price != null` → `currency` must be known (ISO 4217 code).
* The application default currency is `EUR`, applied explicitly when the
  user provides a price without choosing a currency.

Conversion to a decimal value happens only at presentation time.

## 2.3 Warranty Status (derived)

`warrantyStatus` is **derived**, never persisted (`DATA_RULES.md` §17):

```text
today < purchaseDate               → future
purchaseDate <= today <= end       → active
today > warrantyEndDate             → expired
```

* `warrantyEndDate` is inclusive: the warranty expires the day **after**
  `warrantyEndDate` (`WARRANTY_END_DATE_RULE.md`).
* The status is calculated in the domain layer from `purchaseDate`,
  `warrantyEndDate`, and the current calendar date. The UI must never
  calculate it independently.
* The warranty starts on the purchase date, so there is no separate warranty
  start date.

## 2.4 Validation

Minimum validation before persistence:

```text
name            != null and not blank
purchaseDate    != null
warrantyEndDate != null
purchaseDate    <= warrantyEndDate
price           == null or price >= 0
currency        known when price != null
```

The only required ordering rule between dates is
`purchaseDate <= warrantyEndDate`. The purchase date is both the start of the
warranty and an informational date (`DATA_RULES.md` §6).

## 2.5 Persistence Rules

* `create`: the application sets `createdAt` and `updatedAt`.
* `update`: `id` and `createdAt` are preserved; `updatedAt` is refreshed.
  Changing dates never implicitly changes other dates (`DATA_RULES.md` §14).
* Search is case-insensitive over `name`, `brand`, `model`, `store`, and
  `serialNumber`, executed by the database.

# 3. Product Documents

A product document (domain entity `WarrantyDocument`) is a file attached to a
product. A product can have multiple documents. Documents belong to the
product rather than to a separate warranty record because the warranty status
is derived from the product dates.

## 3.1 Fields

| Field         | Dart type        | SQLite type | Required | User entered | Notes                                              |
| ------------- | ---------------- | ----------- | -------: | -----------: | -------------------------------------------------- |
| `id`          | `int?`           | `INTEGER`   |      Yes |           No | Primary key, auto-increment                        |
| `productId`   | `int?`           | `INTEGER`   |      Yes |           No | References `products.id`, `ON DELETE CASCADE`      |
| `fileName`    | `String`         | `TEXT`      |      Yes |           No | Original file name shown to the user               |
| `storagePath` | `String`         | `TEXT`      |      Yes |           No | Path relative to the application documents folder  |
| `mimeType`    | `String`         | `TEXT`      |      Yes |           No | Validated MIME type                                |
| `sizeBytes`   | `int`            | `INTEGER`   |      Yes |           No | File size in bytes                                 |
| `source`      | `DocumentSource` | `TEXT`      |      Yes |           No | `scan`, `photo` or `file`                          |
| `createdAt`   | `DateTime`       | `DATETIME`  |      Yes |           No | Set by the application when the document is saved  |

## 3.2 File Storage

* Document metadata is stored in SQLite; document files are stored outside the
  database.
* Files live at
  `<application documents>/warranty_documents/<productId>/<storedName>`.
* `storagePath` stores `warranty_documents/<productId>/<storedName>`. The
  absolute path is resolved at runtime and never persisted.
* Files selected or captured while editing are staged in
  `<application documents>/warranty_documents/.staging` and moved into the
  product folder only when the product is saved.
* Supported file types are PDF, JPG/JPEG, PNG, HEIC, and WEBP. Each file is
  limited to 25 MB.
* Deleting a product cascades to its document metadata. Stored files are
  removed by the documents repository as part of product deletion.

# 4. Reminder Settings

Reminder preferences are **device-local settings**. They are not part of the
product data model, are not stored in SQLite, and are not synchronized with
product or document data. The database `schemaVersion` stays at 3.

| Setting    | Type   | Storage key           | Default | Allowed values   |
| ---------- | ------ | --------------------- | ------- | ---------------- |
| `enabled`  | `bool` | `reminders.enabled`   | `false` | `true` / `false` |
| `leadDays` | `int`  | `reminders.lead_days` | `30`    | 1, 3, 7, 14, 30, 60 |

* `ReminderSettingsRepository` is the only place that knows these storage keys.
* Unknown stored values fall back to the defaults, so a stale or edited
  preference file cannot prevent the app from starting.
* Notification permission is an OS-level state, not an app preference. It is
  read from the notification gateway and is never persisted locally.
* Pending notifications are derived data and are not persisted. They are
  recomputed from the current products and settings on startup, after product
  mutations, and after settings changes.
