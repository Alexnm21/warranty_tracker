# Warranty Tracker — Field Requirements

## 1. Purpose

This document defines which product fields are required, which are optional, and how they should be validated.

It is the source of truth for:

* Product creation.
* Product editing.
* Form requirements.
* Domain validation.
* Persistence requirements.

The data types and persistence representation are defined in `DATA_MODEL.md`.

Date-specific rules are defined in:

`docs/DATE_RULES.md`

Invalid date validation is defined in:

`docs/INVALID_DATE_VALIDATION.md`

---

# 2. Required Fields

The following fields are required for every `Product`:

```text
id
name
purchaseDate
warrantyStartDate
warrantyEndDate
createdAt
updatedAt
```

Some of these fields are managed automatically by the application.

## 2.1 User-entered required fields

The user must provide:

```text
name
purchaseDate
warrantyStartDate
warrantyEndDate
```

## 2.2 System-managed required fields

The application manages:

```text
id
createdAt
updatedAt
```

The user must not be required to enter these fields manually.

---

# 3. Optional Fields

The following fields are optional:

```text
brand
model
store
price
currency
serialNumber
notes
```

Optional information must not prevent the user from creating a valid product.

---

# 4. Field Requirements

| Field               |    Required | User entered | Validation                         |
| ------------------- | ----------: | -----------: | ---------------------------------- |
| `id`                |         Yes |           No | Must be unique and stable          |
| `name`              |         Yes |          Yes | Must not be empty                  |
| `brand`             |          No |          Yes | Empty value becomes `null`         |
| `model`             |          No |          Yes | Empty value becomes `null`         |
| `store`             |          No |          Yes | Empty value becomes `null`         |
| `purchaseDate`      |         Yes |          Yes | Must be provided                   |
| `price`             |          No |          Yes | Must be non-negative               |
| `currency`          | Conditional |          Yes | Required when `price` is provided  |
| `serialNumber`      |          No |          Yes | Empty value becomes `null`         |
| `warrantyStartDate` |         Yes |          Yes | Must be provided                   |
| `warrantyEndDate`   |         Yes |          Yes | Must be provided and >= start date |
| `notes`             |          No |          Yes | Empty value becomes `null`         |
| `createdAt`         |         Yes |           No | Generated by the application       |
| `updatedAt`         |         Yes |           No | Managed by the application         |

---

# 5. Name

`name` is required.

The value:

* Must not be empty.
* Must not contain only whitespace.
* Should be trimmed before validation and persistence.

Example:

```text
""
→ invalid

"   "
→ invalid

" iPhone 17 "
→ valid
```

The persisted value should be normalized to:

```text
"iPhone 17"
```

The application should not impose an arbitrary maximum length unless a concrete requirement appears.

---

# 6. Brand

`brand` is optional.

If the user does not provide a brand:

```text
brand = null
```

An empty string should not normally be persisted:

```text
""
```

Instead:

```text
null
```

The value should be trimmed before persistence.

---

# 7. Model

`model` is optional.

If not provided:

```text
model = null
```

The value should be trimmed before persistence.

No strict format should be imposed because product model identifiers vary considerably between manufacturers.

---

# 8. Store

`store` is optional.

If not provided:

```text
store = null
```

The value should be trimmed before persistence.

The initial version treats the store as free text.

No dedicated `Store` entity is required.

---

# 9. Purchase Date

`purchaseDate` is required.

It represents the calendar date on which the product was purchased.

The application should use a date picker or equivalent date-selection UI.

The purchase date is informational and does not determine warranty status.

There is currently no validation requiring:

```text
purchaseDate <= warrantyStartDate
```

or:

```text
purchaseDate <= warrantyEndDate
```

The purchase date may legally occur:

* Before the warranty starts.
* On the warranty start date.
* During the warranty period.
* After the warranty has ended.

These cases are valid under the current business rules.

---

# 10. Price

`price` is optional.

When provided:

* It must not be negative.
* Zero is valid.
* It must be represented using integer minor currency units.

Example:

```text
899.99 EUR
→ 89999
```

Do not use floating-point values for persisted monetary amounts.

If no price is provided:

```text
price = null
```

---

# 11. Currency

`currency` identifies the currency associated with `price`.

It should use an ISO 4217 currency code.

Examples:

```text
EUR
USD
GBP
```

The relationship is:

```text
price == null
    → currency may be omitted/defaulted according to application behavior

price != null
    → currency must be known
```

If the application uses a default currency for new products, that default should be applied explicitly rather than treating an unknown currency as valid.

The initial application may use:

```text
EUR
```

as its default currency.

---

# 12. Serial Number

`serialNumber` is optional.

It must be stored as a string.

If not provided:

```text
serialNumber = null
```

Do not attempt to parse serial numbers as numeric values.

Serial numbers may contain:

* Letters.
* Numbers.
* Hyphens.
* Other manufacturer-specific characters.

The value should be trimmed before persistence.

---

# 13. Warranty Start Date

`warrantyStartDate` is required.

It represents the first calendar day covered by the warranty.

The date is inclusive.

Therefore:

```text
today == warrantyStartDate
```

means the warranty is:

```text
active
```

The start date must satisfy:

```text
warrantyStartDate <= warrantyEndDate
```

No relationship with `purchaseDate` is required.

---

# 14. Warranty End Date

`warrantyEndDate` is required.

It represents the last calendar day covered by the warranty.

The date is inclusive.

Therefore:

```text
today == warrantyEndDate
```

means the warranty is still:

```text
active
```

It becomes expired on:

```text
warrantyEndDate + 1 day
```

The end date must satisfy:

```text
warrantyEndDate >= warrantyStartDate
```

A same-day warranty is valid:

```text
warrantyStartDate == warrantyEndDate
```

---

# 15. Notes

`notes` is optional.

If not provided:

```text
notes = null
```

Empty or whitespace-only notes should normally be converted to `null`.

Notes are intended for unstructured additional information.

Structured information should use its dedicated field whenever one exists.

---

# 16. Created At

`createdAt` is required but system-managed.

It represents when the product was created in the application.

The user does not enter this value.

It must remain unchanged after creation.

---

# 17. Updated At

`updatedAt` is required but system-managed.

It represents the most recent modification to the persisted product.

When a product is updated:

```text
updatedAt
```

must be updated accordingly.

The user does not enter this value.

---

# 18. Warranty Status

Warranty status is not a user-entered field.

It is derived from:

```text
warrantyStartDate
warrantyEndDate
today
```

Possible states:

```text
future
active
expired
```

The rules are:

```text
today < warrantyStartDate
    → future

warrantyStartDate <= today <= warrantyEndDate
    → active

today > warrantyEndDate
    → expired
```

The status must not be persisted as an independent source of truth.

---

# 19. Warranty Duration

Warranty duration is not a user-entered field.

It is derived from:

```text
warrantyStartDate
warrantyEndDate
```

Do not require the user to enter:

```text
duration
months
years
```

when the actual start and end dates are already available.

---

# 20. Form Behavior

The product form must:

1. Require the four user-entered required fields.
2. Allow optional fields to remain empty.
3. Trim text values before persistence.
4. Convert empty optional text fields to `null`.
5. Validate the warranty date range.
6. Preserve entered values when validation fails.
7. Show validation feedback near the relevant field when practical.
8. Avoid silently changing one date because another date was changed.
9. Prevent persistence when required validation fails.

The form should not make optional fields mandatory without an explicit product decision.

---

# 21. Validation Responsibilities

Validation should exist at the appropriate layers.

### Presentation

Responsible for:

* Immediate user feedback.
* Required form fields.
* Field formatting.
* User-friendly validation messages.

### Domain/Application

Responsible for:

* Important business rules.
* Warranty date relationships.
* Protection against invalid products being created through non-UI paths.

### Data

Responsible for:

* Persistence constraints.
* Database-specific requirements.

The database should not be the only place where business validation occurs.

---

# 22. Initial Required User Information

To create a product, the user must provide:

```text
Product name
Purchase date
Warranty start date
Warranty end date
```

Everything else may initially be left empty or use an application-defined default where appropriate.

This keeps product creation simple while allowing additional information to be added later.

---

# 23. Future Changes

A field should only become required after an explicit product decision.

For example, do not make:

```text
brand
model
store
serialNumber
price
```

mandatory merely because the application may benefit from having that information.

If a new required field is introduced:

1. Update this document.
2. Update `DATA_MODEL.md`.
3. Update the relevant UI.
4. Update validation.
5. Update tests.
6. Consider database migration requirements.

---

# 24. Final Rules

The minimum valid product requires:

```text
name
purchaseDate
warrantyStartDate
warrantyEndDate
```

The system additionally requires:

```text
id
createdAt
updatedAt
```

The warranty dates must satisfy:

```text
warrantyStartDate <= warrantyEndDate
```

The purchase date has no ordering constraint relative to the warranty dates.

Optional information must remain optional.

Do not introduce additional required fields without an explicit product decision.
